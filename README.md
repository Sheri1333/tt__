# Funnel Platform

Мини-платформа для запуска, версионирования и анализа многошаговых веб-воронок.
Fullstack TypeScript: React (Vite) + Node.js (Express 5) + SQLite (встроенный `node:sqlite`), один репозиторий, без сторонних сервисов.

| Адрес | Что это |
|---|---|
| `/` | воронка (рендерится целиком из JSON-конфига с backend) |
| `/?variant=B` | QA-override варианта эксперимента |
| `/?utm_source=…&utm_medium=…&utm_campaign=…` | UTM-метки фиксируются за сессией при её создании |
| `/admin` | версии: загрузка, публикация, откат, журнал релизов |
| `/dashboard` | аналитика по уникальным сессиям |

---

## Старт

Нужен Node.js ≥ 22.13 (в нём `node:sqlite` работает без флага; нативных зависимостей нет).

```bash
npm install
npm run build        # собрать фронтенд в dist/client
npm start            # http://localhost:3000; при первом старте подтягивается и публикуется configs/funnel-v1.json
```

Режим разработки (API на :3000 + Vite с HMR на :5173):

```bash
npm run dev
```

Тестовый трафик (сервер должен быть запущен):

```bash
npm run generate                       # 150 сессий на активной версии
npm run scenario                       # полный релизный сценарий: v1 → v2 → v3 → rollback (см. ниже)
npm run generate -- --sessions 300 --seed 42 --url https://host --token $ADMIN_TOKEN
```

Остальное:

```bash
npm test             # vitest: 26 тестов
npm run typecheck
npm run reset-db     # удалить локальную БД (data/funnel.db)
```

Переменные окружения: `PORT` (3000), `DB_FILE` (`data/funnel.db`), `ADMIN_TOKEN` — если задан, `/admin`, `/dashboard` и `/api/admin/*` требуют токен (страница сама его спросит). Без него внутренние страницы открыты (dev-режим).

### Деплой

`Dockerfile` (образ собирает фронт и прогоняет тесты при сборке) и `render.yaml` (Render Blueprint: Docker + постоянный диск 1 ГБ под SQLite + сгенерированный `ADMIN_TOKEN`). Подойдёт любой хостинг с Docker и постоянным томом (`/data`). Без постоянного тома данные будут теряться при каждом рестарте.

## Архитектура

```
configs/            funnel-v1/v2/v3.json — исходные конфиги (v1 публикуется при первом старте)
shared/             общий для клиента, сервера и генератора движок воронки
  types.ts          типы конфига, сессии, событий
  engine.ts         условия, видимость шагов, прогресс, валидация, правила результата, A/B-бакетинг
server/
  db.ts             SQLite + forward-only миграции (применяются автоматически)
  configValidation.ts  zod-схема + семантические проверки ссылок
  versions.ts       неизменяемые версии, активация, откат по стеку активаций
  sessions.ts       создание/возобновление сессий, закрепление версии и варианта, сохранение состояния
  events.ts         идемпотентный пакетный приём событий
  analytics.ts      агрегаты по уникальным сессиям (чистые функции + отчёт)
  app.ts            HTTP API + раздача SPA
client/src/
  funnel/           универсальный рендерер шагов (без захардкоженных экранов)
  tracker.ts        очередь событий в localStorage, батчинг, ретраи, sendBeacon
  admin/ dashboard/ внутренние страницы
scripts/generate-traffic.ts   генератор синтетического трафика с проверкой против dashboard
tests/              vitest + supertest на in-memory SQLite
```

Ключевое решение — **один движок `shared/engine.ts`** для клиента и сервера. Клиент по нему считает навигацию и прогресс, сервер — повторно валидирует ответы и вычисляет результат, генератор — ходит по тем же веткам. Расхождение логики между фронтом и бэком невозможно по построению.

### Динамическая воронка

- Клиент получает от `POST /api/sessions` **уже разрешённый** конфиг: только свой вариант, шаги в порядке `stepSequence`, с применёнными `stepOverrides`/`resultOverrides`. Второй вариант на клиент не уходит.
- Типы шагов: `info`, `single-select` (автопереход по клику), `multi-select` (min/max, лишние опции блокируются), `number` (min/max/step, unit), `result` (loading → результат / ошибка с retry, CTA раскрывает рекомендации).
- Условия: `all` / `any` / `not` + операторы `eq, neq, in, nin, contains, gt, gte, lt, lte, exists`.
- **Видимость считается за один проход по последовательности**: шаг видим, если его `visibleWhen` истинно на ответах *предыдущих видимых* шагов. Ответы на шаги, ставшие скрытыми (например, `office_days` после смены `hybrid → remote`), игнорируются и в ветвлении, и в результате.
- **Прогресс** = позиция среди *видимых сейчас* шагов, исключая `info`/`result` (`progress.excludeTypes`). Выбор `hybrid` меняет «2 of 7» на «3 of 8».
- **Валидация** — по правилам и текстам из `validation.messages`; на клиенте для UX, на сервере повторно при каждом сохранении состояния (422, если ответ не валиден или вопроса нет в закреплённой версии).
- **Состояние**: источник истины — сервер (`answers` + `path`, стек посещённых шагов). Сохраняется на каждом переходе; `session_id` лежит в localStorage. Refresh / повторное открытие вкладки возвращают ровно на тот же шаг с теми же ответами. На время сохранения/офлайна есть «грязное» зеркало в localStorage, которое при следующем старте досохраняется. Кнопка Back в UI и кнопка «Назад» браузера работают одинаково (`history.pushState` + `popstate`).
- Результат вычисляется **на сервере** (`POST /api/sessions/:id/result`) по сохранённым ответам и закреплённой версии.

### Версии и откаты

- Версия = неизменяемая запись `(funnel_id, version, config JSON, checksum)`. Повторная загрузка того же содержимого — no-op (200), другое содержимое под тем же номером — 409.
- Публикация = смена указателя `funnel_active` + запись в `release_log`. **Без передеплоя**: загрузить JSON через `/admin` (файл, textarea или кнопка «Upload & publish» у конфигов из `configs/`) или `POST /api/admin/versions?publish=true`.
- **Откат** проигрывает журнал как стек: publish/activate — push, rollback — pop. Значит, `v1 → v2 → v3`, rollback → v2, rollback → v1 (а не «качели» обратно на v3).
- **Закрепление**: сессия хранит `version` и `variant`. Возобновление сессии всегда отдаёт её версию, даже если активна другая или эта версия была откачена. Новые сессии — только на активной версии. Сессия живёт `session.ttlHours` (скользящий TTL), после истечения создаётся новая на активной версии.

### A/B-эксперимент

- Назначение на сервере при создании сессии: `FNV-1a(experiment_id + ":" + session_id) mod Σweights` → детерминированно и с учётом весов. Хранится в сессии, поэтому стабильно после refresh и не меняется при публикации новой версии.
- Override: `?variant=B` (имя параметра — `experiment.overrideQueryParam`). Если у существующей сессии другой вариант, создаётся **новая** сессия (вариант существующей никогда не мутирует). Такие сессии помечаются `variant_source = 'override'` и исключаются на dashboard галочкой «Exclude QA overrides».
- Вариант меняет тексты (`stepOverrides`), порядок/набор шагов (`stepSequence`) и экран результата (`resultOverrides`).

**Гипотеза.** Если начинать с вопросов о контексте команды (режим работы, встречи, часовые пояса) вместо «сколько вас человек», пообещать конкретную пользу во вступлении («Is your team losing time…?») и сформулировать результат как проблему с действием («Meetings are consuming your operating capacity» + «Reveal the first three changes»), то пользователи будут чаще доходить до результата и кликать CTA, потому что первые вопросы воспринимаются как релевантные, а результат — как персональный диагноз, а не ярлык.

**Основная метрика** — *Start → CTA*: доля уникальных начавших сессий, кликнувших основной CTA (`cta_clicked` / `session_started`). Она ловит обе части гипотезы (дохождение и клик) и не обманывается ростом CTR на меньшей базе.
**Вспомогательные**: completion rate (start → result), CTR (result → CTA), отвал по шагам. **Guardrail**: отвал на первом вопросе и доля `balanced` (дефолтного результата).
Dashboard показывает Δ в п.п. и p-value двустороннего z-теста для двух долей. Решение принимается внутри одной версии: эксперимент у каждой версии свой (`experiment.id` различается), смешивать версии в одном сравнении нельзя.

## Модель данных

| Таблица | Назначение |
|---|---|
| `funnel_versions(funnel_id, version, config, checksum, release_note, created_at)` | неизменяемые версии конфигов, PK `(funnel_id, version)` |
| `funnel_active(funnel_id, version, updated_at)` | указатель на активную версию |
| `release_log(id, funnel_id, action, from_version, to_version, at)` | append-only журнал publish/activate/rollback |
| `sessions(id, funnel_id, version, experiment_id, variant, variant_source, utm_*, state, created_at, updated_at, expires_at)` | сессия с закреплёнными версией/вариантом/UTM; `state` = ответы + путь — **только для возобновления, в аналитику не попадает** |
| `events(event_id PK, session_id, name, funnel_id, funnel_version, experiment_id, variant, step_id, utm_*, client_timestamp, server_timestamp, properties)` | события; `properties` — JSON, поэтому новые события и свойства не требуют миграций |
| `schema_migrations` | применённые миграции (forward-only, автоматически при старте) |

## Event schema

`POST /api/events` с телом `{"events": [...]}` (до 500 штук). Также принимается `text/plain` — для `navigator.sendBeacon`.

```jsonc
{
  "event_id": "uuid",                 // ключ идемпотентности, [A-Za-z0-9:_.-]{8,128}
  "session_id": "uuid",
  "name": "step_completed",
  "client_timestamp": "2026-10-05T10:00:00.000Z",
  "step_id": "work_mode",
  "funnel_id": "workstyle-planner",   // опционально: сервер всё равно берёт из сессии;
  "funnel_version": 2,                //   если прислано и не совпадает с сессией → reject
  "experiment_id": "…", "variant": "B",
  "utm_source": "…", "utm_medium": "…", "utm_campaign": "…",
  "properties": { "next_step_id": "meeting_hours" }
}
```

Ответ всегда `200` (если конверт корректен) с исходом по каждому событию:

```json
{ "accepted": ["…"], "duplicates": ["…"], "rejected": [{ "index": 3, "event_id": "…", "reason": "unknown_step_id" }] }
```

| Событие | Кто шлёт | `step_id` | properties |
|---|---|---|---|
| `session_started` | **только сервер**, в одной транзакции с созданием сессии | — | `variant_source` |
| `step_viewed` | клиент, при каждом показе шага | шаг | `step_type, visible_step_index, visible_step_count` |
| `answer_submitted` | клиент, валидный ответ | шаг | `answer_kind` (`number`, `single-select`, `multi:2`) |
| `step_completed` | клиент, переход вперёд с интерактивного шага | шаг | `next_step_id` |
| `back_clicked` | клиент, кнопка Back или «Назад» браузера | шаг, *с которого* ушли | `destination_step_id` |
| `result_viewed` | клиент | `result` | `result_id` |
| `cta_clicked` | клиент | `result` | `result_id, action` |
| `recommendation_expanded` (с v3) | клиент, после CTA, если событие объявлено в версии | `result` | `result_id, action, source` |

**Инварианты приёма**
- `event_id` — PRIMARY KEY, вставка `INSERT OR IGNORE` → повтор (в т.ч. внутри одной пачки и после timeout) не создаёт дубль и возвращается в `duplicates`.
- Каждое событие валидируется отдельно; плохое попадает в `rejected` с причиной, остальная пачка сохраняется (одна транзакция на пачку, исключения ловятся по событию).
- `funnel_version`, `variant`, `experiment_id`, UTM **проштамповываются из серверной сессии** — устаревший клиент не может испортить разрез.
- Разрешённые имена событий берутся из `events.allowed` **закреплённой версии сессии**: `recommendation_expanded` принимается от сессий v3 и отклоняется (`event_not_allowed_in_v1`) от v1/v2.
- `properties` фильтруются по белому списку события из конфига: сырые ответы (`raw_value`, email и т.п.) отбрасываются, даже если клиент их пришлёт. В аналитику попадает только `answer_kind`. Сырые ответы живут только в `sessions.state`, чтобы можно было возобновить сессию и посчитать результат.
- `session_started` клиенту слать запрещено (`server_only_event`); клиентское время со сдвигом больше 7 дней сохраняется с флагом `_clock_skew`.

**Клиентская доставка**: событие получает `event_id` в момент создания и сразу пишется в очередь в localStorage; пачки до 50 штук каждые 1,5 с; из очереди удаляется только то, на что сервер ответил; при timeout/ошибке сети та же пачка (с теми же id) повторяется с экспоненциальной задержкой; при скрытии вкладки — `sendBeacon`.

## Правила агрегации

Реализованы в `server/analytics.ts`, покрыты тестами `tests/analytics.test.ts`.

1. **Только уникальные сессии.** Дубли `event_id` отсекаются при приёме; повторные `step_viewed` (refresh, возврат назад) схлопываются в множество сессий. В таблице шагов отдельно показаны сырые `Views`, чтобы повторы были видны.
2. **Независимость от порядка.** Время событий не используется для определения позиции в воронке. Прогресс сессии — самый дальний шаг (по индексу в последовательности *её* варианта), по которому есть хоть какое-то свидетельство. Поэтому опоздавшие или переставленные события просто дополняют те же множества.
3. **Неявное достижение.** Более поздний этап подразумевает более ранний: начатая сессия ⇒ первый шаг достигнут (сервер отдаёт его вместе с сессией); `answer_submitted` / `step_completed` / `back_clicked` ⇒ шаг достигнут; любой более поздний шаг ⇒ этот шаг пройден; `cta_clicked` ⇒ результат показан. Потерянные события не дают конверсий больше 100%.
4. **Метрики:**
   - *Started* = уникальные сессии (у каждой есть серверный `session_started`).
   - *Reached* шага = сессии со свидетельством шага; *→ Next* = доля достигших, кто прошёл дальше; это и есть конверсия между шагами, корректная при ветвлении (условный шаг помечен `if`, его «Reached» по построению меньше).
   - *Drop-off* шага = сессии, чей самый дальний шаг — этот, и которые не дошли до результата. Сумма отвалов + дошедшие до результата = Started.
   - *Completion* = result / started, *CTR* = CTA / result, *Start → CTA* = CTA / started.
   - Возвраты назад не уменьшают самый дальний шаг; *Back* — уникальные сессии, нажавшие «назад» на шаге.
5. **Разрезы**: версия × вариант (у каждой версии своя последовательность шагов), фильтр по `utm_campaign` (включая «(none)»), исключение QA-override.

## Генератор трафика

`scripts/generate-traffic.ts` работает через публичный HTTP API (локально или против деплоя) и:

- создаёт сессии с 5 UTM-источниками/кампаниями (включая direct) — вариант назначает сервер;
- проходит разные ветки (случайные ответы → `office_days`, `security_constraints`, разные результаты);
- отваливается на разных шагах (вероятность зависит от варианта, типа шага и кампании; в модель заложена гипотеза «B лучше»);
- нажимает Back и меняет ответы, повторно показывает шаги (refresh);
- доставляет события с хаосом: дубль внутри пачки (~6% пачек), **повторная отправка той же пачки** (~10%), **обратный порядок пачек** (~12% сессий), невалидные события (~3%);
- в режиме `--scenario` проигрывает релизную историю: v1-трафик с незавершёнными сессиями → publish v2 → незавершённые v1-сессии возобновляются и **доигрывают на v1** → publish v3 → rollback на v2 → незавершённые v3-сессии доигрывают на v3 (их `recommendation_expanded` принимаются) → новая сессия стартует на v2;
- ведёт собственную «истину» и в конце **сверяет приращение dashboard** (started / result / CTA по версии × варианту) с ней. Несовпадение → exit code 1. Детали (отвал по шагам, распределение результатов, статистика доставки) → `generator-report.json`.

Пример вывода `npm run scenario -- --sessions 180 --seed 42` (числа меняются от прогона к прогону: `--seed` фиксирует поведение пользователей, а варианты назначает сервер по случайным `session_id`):

```
  ✓ 10 in-flight v1 sessions resumed and finished on v1 after v2 was published
  rolled back → active v2
  ✓ 8 in-flight v3 sessions finished on v3 after rollback (recommendation_expanded accepted)
  ✓ new sessions start on v2
│ v1 │ A │ '26 / 26' │ '16 / 16' │ '5 / 5'   │ ✓ │
│ v1 │ B │ '34 / 34' │ '23 / 23' │ '13 / 13' │ ✓ │
│ v2 │ A │ '35 / 35' │ '17 / 17' │ '11 / 11' │ ✓ │ ...
Delivery chaos: { batches: 1018, retriedBatches: 97, reversedSessions: 24, inBatchDuplicates: 55, duplicates: 455, rejected: 29 }
✓ Dashboard matches the simulated ground truth
```

## Вторая итерация (v3)

Изменения v3: условная ветка `security_constraints` (только если в `priorities` выбрано `compliance`), удалён `tool_count` у варианта B, новый результат `regulated_scale`, новое событие `recommendation_expanded`.

**Код и схему БД менять не потребовалось** — это и было целью архитектуры первой итерации:
- новый шаг/ветка/результат — данные конфига, движок универсален (`contains` уже поддерживался);
- новое событие — строка в `events.allowed`; приём проверяет его по версии сессии, таблица `events` общая;
- клиент шлёт `recommendation_expanded` только если оно объявлено в его версии (`supportsEvent`), так что v1/v2-сессии не начинают слать неизвестное событие;
- удалённый у B экран просто отсутствует в `stepSequence`; аналитика строит воронку по последовательности конкретной версии × варианта, поэтому v2-аналитика не ломается.

Порядок проверки:
1. `/admin` → `funnel-v3.json` → *Upload & publish* (или `POST /api/admin/versions?publish=true`).
2. Новые сессии на v3; `?variant=B` → нет `tool_count`, выбор `compliance` открывает `security_constraints`; `strict`/`regulated` → результат `regulated_scale`; CTA шлёт `cta_clicked` + `recommendation_expanded`.
3. Начатые до публикации сессии v1/v2 продолжаются на своих версиях (refresh — то же место, те же шаги).
4. *Roll back* → активна предыдущая версия; новые сессии на ней, сессии v3 доигрывают на v3.
5. Dashboard: аналитика v1/v2 не изменилась, в «Versions» появилась v3, в таблице событий v3 — `recommendation_expanded`.

Всё это автоматически проигрывает `npm run scenario` и частично покрывают тесты.

## Ограничения и допущения

- **Одна воронка** (`workstyle-planner`) в UI; API и схема уже принимают `funnelId`.
- **Аналитика считается в памяти** по событиям, выбранным SQL-фильтром. Для тысяч сессий это мгновенно; для миллионов нужны предагрегаты (материализованные таблицы «сессия → самый дальний шаг» с инкрементальным обновлением).
- **Admin-доступ** — один общий токен (`ADMIN_TOKEN`), без пользователей и ролей.
- **Версия в конфиге задаёт номер версии**; номера неизменяемы, исправление = новая версия.
- **Сырые ответы** хранятся в `sessions.state` (нужны для возобновления и серверного результата), но никогда не копируются в `events`. Очистка состояния истёкших сессий не реализована.
- `step_completed` шлётся только для интерактивных шагов (как в описании события); прохождение `intro` выводится из достижения следующего шага.
- Повторный `result_viewed` при refresh на экране результата ожидаем — считается по уникальным сессиям.
- **Back к шагу, открытому до перезагрузки страницы**, выполняется внутри приложения (запись истории заменяется), потому что записи истории браузера, созданные до перезагрузки, не принадлежат текущему документу.
- **Значимость**: z-тест без поправок на подглядывание; на синтетических 100–300 сессиях разница чаще всего не значима — это ожидаемо, нужен расчёт размера выборки до запуска.
- **Часы клиента** не используются для логики; хранятся оба времени (`client_timestamp`, `server_timestamp`).
- `node:sqlite` в Node 22 помечен как experimental (выдаёт предупреждение). Выбран, чтобы не тащить нативные сборки; переход на `better-sqlite3` — замена одного файла `server/db.ts`.
